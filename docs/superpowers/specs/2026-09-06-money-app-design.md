# fianc — Personal Money Manager: Design

**Date:** 2026-09-06
**Status:** Approved for planning

## Purpose

A personal finance web app for one to two people. Its job is to answer two
questions quickly: where did the money go this month, and how much is left to
spend. It is a transaction ledger with per-category monthly budgets on top.

It is installable as a PWA and designed mobile-first, because most transactions
are entered on a phone shortly after they happen. Desktop gets its own layout
rather than a stretched phone layout, because reviewing and correcting a month
of history is a desktop task.

### Success criteria

- Adding a transaction on a phone takes under ten seconds from app icon to saved.
- The dashboard shows month-to-date income, expense, net, and remaining budget
  without a page reload after any edit.
- A bank CSV export can be imported, deduped against existing rows, and undone
  in one action.
- Budget rollover is correct across months with no budget set and across months
  that were overspent.

### Out of scope for v1

Bank sync (Plaid or similar), multiple currencies, receipt attachments, a native
mobile app, sharing a ledger between users, trend and net-worth reports, and
offline mutation queueing. Each is deferred, not rejected.

## Stack

| Concern | Choice | Reason |
|---|---|---|
| Framework | Next.js 15, App Router, TypeScript | Server actions remove the need for a separate API layer |
| Styling | Tailwind v4, shadcn/ui, Lucide icons | `DESIGN.md` is written against these tokens |
| Database | Supabase Postgres via Drizzle + postgres.js | Managed Postgres; Drizzle keeps schema in TypeScript |
| Auth | Hand-rolled sessions (see below) | Two known users, invite-free, no external dependency |
| Validation | Zod | One schema shared by the form and the server action |
| Charts | Recharts | Composes with the token palette |
| PWA | Serwist | Maintained successor to `next-pwa`, App Router aware |
| Tests | Vitest, Playwright | Unit for logic modules, e2e for the critical path |

Fonts: Geist via `next/font`. Icons: Lucide only — **no emoji anywhere in the
UI**.

### Database access

The browser never talks to Postgres. There is no `supabase-js` client, no anon
key, and no Row Level Security. Supabase supplies a managed Postgres instance
and nothing else; every query runs in server code that already scopes by
`user_id`. RLS would be a second enforcement of a rule the query layer already
enforces, and a second place for it to be wrong.

The pooled connection string lives in `DATABASE_URL` and is server-only.

## Authentication

Self-built, deliberately minimal, sized for two users and non-sensitive data.

- **Passwords** hashed with argon2id (`@node-rs/argon2`) at library defaults.
- **Sessions**: 32 random bytes, base64url-encoded, sent as the cookie value.
  Only the SHA-256 of that value is stored in `sessions.token_hash`, so a
  database read does not yield usable session tokens.
- **Cookie**: `httpOnly`, `SameSite=Lax`, `Secure`, 30-day expiry, refreshed
  when a request arrives with more than half the lifetime elapsed.
- **Signup** requires a code matching the `SIGNUP_CODE` environment variable.
  There is no open registration and no invites table.
- **Middleware** (`middleware.ts`) checks only for cookie presence and redirects
  unauthenticated requests. It does not hit the database. Real validation lives
  in `getSession()`, cached per request with `React.cache`, called by the
  protected layout and by every server action.
- **Logout** deletes the session row, not just the cookie.

Not included, by decision: email verification, password reset by email, MFA,
rate limiting, and audit logging. Password change requires the current password
and is done from Settings.

## Data model

All money is stored as **integer minor units** in `bigint` columns — cents, not
dollars, never floating point. A single base currency is stored on the user.

All ids are UUIDs generated by the database. All user-owned tables carry
`user_id` and are indexed on it.

### `users`
`id`, `email` (text, stored lowercased, unique), `password_hash`, `name`, `base_currency`
(ISO 4217, default `USD`), `created_at`.

### `sessions`
`id`, `user_id`, `token_hash` (unique), `expires_at`, `created_at`.
Expired rows are deleted opportunistically on login.

### `accounts`
`id`, `user_id`, `name`, `type` (`checking` | `savings` | `cash` |
`credit_card` | `investment`), `opening_balance` (minor units, signed),
`sort_order`, `archived_at`, `created_at`.

Balance is never stored. It is `opening_balance` plus a `SUM` over the
account's transactions, computed on read.

### `categories`
`id`, `user_id`, `name`, `kind` (`income` | `expense`), `parent_id` (nullable,
self-reference, one level deep only), `icon` (a Lucide icon name),
`archived_at`, `created_at`.

Archived categories keep their historical transactions but do not appear in
pickers.

### `transactions`
`id`, `user_id`, `account_id`, `category_id` (nullable), `type` (`income` |
`expense` | `transfer`), `amount_minor` (**always positive**; direction comes
from `type`), `date`, `payee`, `note`, `transfer_group_id` (nullable),
`recurring_rule_id` (nullable), `occurrence_date` (nullable),
`import_batch_id` (nullable), `dedupe_hash` (nullable), `created_at`,
`updated_at`.

Indexes: `(user_id, date desc)`, `(user_id, category_id, date)`,
`(user_id, account_id, date)`, unique `(recurring_rule_id, occurrence_date)`,
unique `(user_id, dedupe_hash)` where `dedupe_hash` is not null.

### `budgets`
`id`, `user_id`, `category_id`, `month` (a date, always the first of the
month), `amount_minor`, `rollover` (boolean), `created_at`.
Unique on `(user_id, category_id, month)`.

### `recurring_rules`
`id`, `user_id`, plus the transaction template (`account_id`, `category_id`,
`type`, `amount_minor`, `payee`, `note`), plus the schedule: `freq`
(`daily` | `weekly` | `monthly` | `yearly`), `interval` (integer, default 1),
`anchor_day` (day of month or weekday, interpreted per `freq`), `start_date`,
`end_date` (nullable), `last_posted_date` (nullable), `paused` (boolean),
`created_at`.

### `import_batches`
`id`, `user_id`, `account_id`, `filename`, `row_count`, `created_at`.
`transactions.import_batch_id` cascades on delete, which makes "undo import" a
single row deletion.

## Three model decisions

### Transfers are two rows

A transfer writes two transactions inside one database transaction, sharing a
`transfer_group_id`: an outflow on the source account and an inflow on the
destination. Neither row has a category.

This keeps every balance and report query as a plain aggregate over
`transactions` with no special case for transfers. The cost is in the UI, which
must group the pair back into a single row for display and edit both halves
together — one localized cost, paid instead of a special case in every query.

Transfers are excluded from income, expense, and budget calculations by
filtering `type <> 'transfer'`.

### Budget rollover is computed, not stored

For a category with rollover enabled:

```
available(m) = budget(m) + carry(m)
carry(m)     = rollover ? available(m-1) - spent(m-1) : 0
```

`carry` is negative when the previous month was overspent, so overspending
eats into the next month. Months with no budget row contribute `budget = 0`
but still carry.

This folds forward from the category's earliest budget month in
`lib/budgets.ts` as a pure function over `(budgets[], spentByMonth[])`. Nothing
is persisted, so a corrected historical transaction fixes every later month for
free. If the fold becomes slow after several years, cache per month then — not
now.

### Recurring transactions post lazily

There is no scheduler. When the app loads, a server action expands each active
rule from `last_posted_date` (or `start_date`) through today and inserts the
due occurrences. The unique index on `(recurring_rule_id, occurrence_date)`
makes the operation idempotent, so concurrent loads cannot double-post.

Nothing posts while nobody opens the app. That is acceptable because the
balances only matter when someone is looking at them. Avoiding a cron job
removes an entire class of operational failure for a two-person app.

Month-end anchors clamp: a rule anchored to the 31st posts on the 30th in
April and on the 28th or 29th in February.

## Application structure

```
app/
  (auth)/login, (auth)/signup        — no app chrome, centered card
  (app)/                             — session guard in the layout
    dashboard  transactions  budgets
    accounts   categories    import   settings
  manifest.webmanifest  sw.ts        — PWA
lib/
  db/{schema,index}.ts
  auth/{password,session,guard}.ts
  money.ts        — parse and format minor units
  budgets.ts      — the rollover fold
  recurring.ts    — occurrence expansion
  csv.ts          — column mapping and dedupe hashing
  queries/*.ts    — read models, every one taking userId as its first argument
components/
  ui/             — shadcn primitives
  responsive/     — ResponsiveDialog, ResponsiveNav, DataList
```

Every module under `lib/` except `db` and `queries` is a pure function module
with no I/O, which is what makes the test suite fast and the logic reviewable.
Server actions stay thin: parse with Zod, call a lib function, persist,
`revalidatePath`.

## Pages

**Dashboard.** Month-to-date stat blocks for income, expense, net, and budget
remaining — typographic, no card chrome, per `DESIGN.md`'s stat block. A
spend-by-category donut, a budget progress list, and the ten most recent
transactions. A month switcher in the header drives all of it.

**Transactions.** Filters for date range, account, category, type, and free
text over payee and note. Server-side pagination and sorting. Add and edit
through a `ResponsiveDialog`. Multi-select with bulk delete. Transfer pairs
render as one row.

**Budgets.** One month at a time, one row per expense category: cap, spent,
remaining bar, and a rollover toggle. Amounts edit inline. A "copy last month"
action seeds a new month.

**Accounts.** Cards showing computed balance, with archive and reorder.

**Categories.** A one-level tree with a Lucide icon picker.

**Import.** Upload, parse with papaparse, map columns to fields, then a preview
that flags rows already present by `dedupe_hash`
(`sha256(account_id | date | amount_minor | payee)`). Committing writes an
`import_batches` row and its transactions in one database transaction. A single
button undoes the whole batch.

**Settings.** Name, base currency, password change, and recurring rule CRUD.

## Mobile, desktop, and PWA

The app is mobile-first: layouts are authored at the phone width and expand at
breakpoints. Desktop is a genuinely different arrangement, not the phone
layout stretched wide.

### Mobile (below `md`)

- A fixed bottom tab bar: Dashboard, Transactions, Budgets, More. Icons with
  labels, respecting `env(safe-area-inset-bottom)`.
- A floating action button for "add transaction", the one action worth a
  permanent affordance.
- Transactions render as a grouped list of tappable rows — date headers, payee
  and category on the left, amount on the right — not a horizontally scrolling
  table.
- Forms and detail views open in a bottom `Drawer` (vaul), which is reachable
  one-handed.
- Touch targets are at least 44px. The amount field opens a numeric keypad
  (`inputMode="decimal"`).

### Desktop (`md` and up)

- The persistent left sidebar from `DESIGN.md`, surface `#fafafa`, with a ⌘K
  command palette at its top.
- Transactions become a real data table: sortable columns, inline editing,
  keyboard row navigation, multi-select.
- Forms open in a `Sheet` or `Dialog`; the FAB and bottom bar are gone.
- The dashboard uses a multi-column grid; mobile stacks it in one column.

### Sharing one component tree

Layout differences are pure CSS at Tailwind breakpoints, so they cost no
JavaScript and cannot mismatch during hydration. Only the components that swap
*structure* — Drawer versus Dialog, bottom bar versus sidebar — need to know
the viewport. Those go through a `ResponsiveDialog` / `ResponsiveNav` pair
backed by a `useMediaQuery` hook built on `useSyncExternalStore`, which gives a
stable server snapshot and therefore no hydration warning.

Rendering both variants and hiding one with CSS is explicitly rejected: it
doubles the DOM and duplicates focus traps.

### PWA

- `manifest.webmanifest` with name, short name, `display: standalone`,
  `theme_color` and `background_color` set to the `DESIGN.md` canvas `#f5f5f5`,
  a maskable 512px icon, and portrait orientation.
- Serwist service worker: precache the app shell, static assets, and fonts;
  `NetworkFirst` for navigations with an offline fallback page;
  `StaleWhileRevalidate` for static assets.
- iOS needs `apple-touch-icon` and `apple-mobile-web-app-*` meta tags; iOS
  ignores `beforeinstallprompt`, so installation there is a documented
  "Add to Home Screen" note in Settings rather than a prompt.
- A custom install prompt on supported browsers, captured from
  `beforeinstallprompt` and shown once, dismissible.

**Offline scope, v1:** read-only. The shell and the last-viewed pages load
offline, but mutations require the network and the UI shows a persistent
offline banner that disables save buttons with an explanation.

Offline write queueing is deferred deliberately. Doing it properly means local
id generation, a replay queue, and conflict resolution against server state —
comparable in size to the rest of the app. A phone that is briefly offline can
wait; the alternative is a sync bug that silently loses a transaction, which is
worse than not being able to add one.

The light theme from `DESIGN.md` is the only theme. No dark mode in v1.

## Error handling

- Server actions return `{ ok: true, data } | { ok: false, error }`. They never
  throw across the client boundary. Zod field errors render inline on the form;
  anything else raises a toast.
- Amount parsing rejects ambiguous input rather than guessing. There is no
  silent coercion through a float.
- A row that exists but belongs to another user returns **not found**, not
  forbidden, so ids do not leak existence.
- Import commit, transfer creation, and recurring catch-up each run inside a
  single database transaction. Partial writes are not possible.
- The unique index on `(user_id, dedupe_hash)` is the real defense against
  double-importing; the preview UI is a convenience on top of it.

## Testing

Development is test-first. The logic worth testing lives in `lib/`, where it is
pure.

**Vitest.**
- `money.ts`: parse and format round-trip, negative and zero handling,
  rejection of ambiguous strings.
- `budgets.ts`: rollover across months with no budget row, across an overspent
  month, and with rollover toggled off mid-year.
- `recurring.ts`: expansion across month ends, leap days, a 31st anchor in
  short months, `interval > 1`, and a rule with an `end_date`.
- `csv.ts`: dedupe hash stability and column mapping edge cases.
- `auth/*`: argon2 verify, session expiry, session refresh, token hashing.

**Playwright.**
- Signup with the code, then log in.
- Add an account, add a transaction, confirm the dashboard and the budget bar
  both update.
- Import a CSV, confirm duplicates are flagged, commit, then undo.
- One mobile-viewport run of the add-transaction path through the drawer.
- A Lighthouse PWA installability check in CI.

## Two small decisions, made

**Seed data.** A first login seeds a default category set (Salary; Groceries,
Rent, Transport, Dining, Utilities, Health, Shopping, Other) with Lucide icons,
all editable and archivable. An empty ledger with an empty category list gives
a new user nothing to do first.

**⌘K command palette.** Deferred to after v1. It is desktop polish over
navigation that already works, and it is the first thing to cut if the build
runs long.
